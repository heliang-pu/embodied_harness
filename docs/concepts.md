# 核心概念

embodied-harness 把一个长任务拆成两层：

- **规划器**决定下一步做哪个子任务。它通常是一个 VLM。
- **策略**把这个子任务做出来，输出机器人动作。它可以是 VLA、WAM（world action model）或任何「看图 + 读一句话 → 出一段动作」的模型。

中间所有的逻辑都在 harness 里：
- 什么时候问规划器，检查它的回答；
- 把子任务换成策略训练时见过的那句提示词；
- 判断子任务做完没有，失败了怎么恢复；
- 记录下全部过程。

模型可以随时换，这部分逻辑不用跟着改。

```
            ┌──────────── 调度器（确定性状态机）────────────┐
 相机、本体 ─►  什么时候问规划器 · 检查回答 · 派发 · 校验 · 恢复  ├─► 轨迹：事件、图片、动作、视频
            └──┬──────────────▲─────────────┬──────────▲─┘
               │ 上下文        │ {技能, 参数, 记忆}  │ 提示词原文  │ 技能结束/失败
               ▼              │             ▼          │
          规划器（VLM）─────────┘       策略（VLA / WAM）   校验器（本体规则、超时）
                                           │
                                           ▼ 动作块
                                      环境 / 机器人
```

## 分工

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 规划器 | 看相机画面、本体状态和自己上次写的记忆，从任务的技能里选下一步，并改写记忆 | 不直接控制机器人，也不决定什么时候被问 |
| 调度器（supervisor） | 状态机，拥有控制流：请求规划、检查回答、派发技能、根据校验结果提交或恢复、预算、保持（HOLD） | 不看图，不做学习 |
| 策略 | 收到当前观测和提示词，返回一段动作（动作块） | 通常只执行当前子任务；`websocket` 执行器也可以通过 `texts` 模板把本 episode 的完整 `goal` 一并传给策略 |
| 校验器 | 每个控制周期用本体规则（比如夹爪宽度）判断当前技能是成功、失败还是还在做 | 不用仿真真值 |
| 环境 | 提供相机、本体，执行动作 | — |

调度器按显式状态和输入选择分支，便于追踪原因。规划器调用可以离线重放比较；中断后恢复账本和记忆、以及支持快照的仿真状态。重放和续跑的具体边界见 [轨迹与排错](debugging.md#重放和续跑)。

## 技能、提示词库、任务

三个配置文件描述一个任务，写法见 [配置参考](configuration.md)。

- **提示词库**（prompt library）列出策略训练时见过的每一句子任务提示词，一字不差，每句有一个 id。它跟着策略权重走：换一个策略就换一份提示词库。
- **技能**（skill）是规划器可以选的动作单元，可以带枚举参数，比如 `place(bin=A)`。技能只引用提示词库的 id，不写原文，所以策略永远只会收到它训练过的句子。技能还定义前置条件、成功和失败条件、超时、失败后的恢复方式，以及成功后对账本的修改。
- **任务**（task）给出目标、规则、可用技能、账本字段、完成条件和预算。换任务只改配置，不改代码。

对于 `openai_compat` JSON 规划器，输出是 `{"skill": ..., "args": {...}, "memory": ...}` 或 `{"done": true, "memory": ...}`；部署时可用 vLLM 的约束解码，限制技能名和参数值。RoboMME 的 `robomme_subgoal` 规划器原始模型输出的是自然语言子目标，适配器再把它映射成同一套内部技能调用；它不使用 JSON 模型的自写记忆。

## 一个 episode 怎么跑

1. `env.reset()`，调度器进入 PLAN，请求第一次规划。
2. 规划器返回决策。调度器依次检查：能否解析成 JSON；技能是否属于这个任务；参数是否合法；前置条件是否满足（例如 `place` 要求 `holding`）。不通过就提高温度重采样（`max_resamples` 次），还不行就 HOLD。
3. 通过后派发（EXECUTE）：把技能换成提示词库里的原文交给策略，指令版本号加一。
4. 每个控制周期：动作队列空了就让策略推理一个动作块，取一个动作执行。校验器同时判断当前技能：
   - 成功：执行技能的 `effects`（更新账本），检查任务的 `done_when`。满足就结束，否则回到 PLAN。
   - 失败：查技能的 `on_failure` 表，按失败原因重试（可以先跑恢复原语）、交回规划器，或进入 HOLD。
5. 任务结束有两种情况：技能成功后账本满足 `done_when`，直接结束；或者规划器声明 `done`，这时也要 `done_when` 成立才算数（没写 `done_when` 时相信规划器，除非 `planner.allow_done: false`：这时不论用哪种规划器、是否约束解码，规划器的 `done` 都不算数，只有环境的终止信号能结束 episode）。不成立的 `done` 和不合法的回答一样算一次被拒绝，它写的记忆不保存：以原因 `check_failed` 提高温度重采样，`show_rejections` 打开时把拒绝原因告诉规划器；同一轮规划里超过 `max_resamples` 次就 HOLD（`E_PLANNER_INVALID`），不会无限地问下去。环境也可以自己结束 episode（比如按下按钮、步数用完），这时 harness 直接停下，读一次环境的成功标志用来评分。harness 自己以 `done` 结束时，环境若报告成功标志（仿真），也读一次记为 `env_success`：有环境结论时按它评分，没有（真机）才按 `done` 评分。

没有技能在执行时（规划中、保持中），harness 每个周期调用 `env.hold()` 让机器人停在原位。

## 调度器的状态

| 状态 | 含义 |
| --- | --- |
| PLAN | 等规划器的决策；超时或出错按 `retries` 和指数退避重试 |
| EXECUTE | 正在执行一个技能 |
| RETRY | 失败后正在执行恢复原语（`before_retry`），然后重试原技能 |
| HOLD | 停住等人：`resume` 让规划器重新规划，`retry` 重新执行 HOLD 所针对的技能，`skip` 把它当作人工完成，`abort` 结束。非交互运行时用 `--hold-policy` 自动回答。详见下面的「HOLD 针对哪个调用」 |
| DONE / ABORT | 结束 |

## 规划器什么时候被问

`planner.call` 有两种：

- `boundary`（默认）：只在技能结束时问。什么时候结束由校验器根据本体判断，规划器只负责决定下一步做什么。调用次数少，适合慢一些的 VLM。
- `periodic`：技能执行中也每 `every_steps` 个控制步问一次，时机选在动作块用完的时候。回答和当前技能相同就继续（这只是确认，不再检查前置条件：`pick` 抓住之后 `not holding` 本来就不成立了）；不同就打断当前技能，换成新的；无效的回答不打断。这是 RoboMME 那类子目标预测器的用法，由模型自己决定什么时候切换。执行中声称 `done` 而不成立时，默认（`done_policy: resample`）打断当前技能，按上面第 5 步重新规划；`done_policy: continue` 时技能继续执行，下一次检查以原因 `check_failed`、按重采样温度再问（`show_rejections` 打开时附上拒绝原因），由环境自己结束 episode。

`periodic` 模式可以配合技能上的 `switch_when` 门控：规划器只有在门控条件成立时才能把当前技能换掉。例如 `place` 的门控是 `released`（夹爪已松开），这样规划器不会在方块还没放下时就跳到下一次抓取。门控只限制执行中的模型切换，不阻止校验器按成功、失败或超时结束技能。每个控制周期校验器先判定，有结论就按结论结束技能，这一拍不再检查；当前技能的成功已经在路上时（成功条件成立了，还在等 `hold_s` 或 `min_duration_s`；没有成功条件的技能是执行器做完了、还没到 `min_duration_s`），不发起新的检查，之前发出、这时才到的回答（`threaded: true`）给出的切换和 `done` 也挡住（`switch_blocked`，`reason: success_pending`），等它判成功、`effects` 记进账本后再问规划器。

## 校验器

每个技能可以写：

- `success`、`failure`：条件列表。条件要连续成立 `hold_s` 秒才算数，单帧噪声不会触发切换。失败条件优先于成功条件，成功条件优先于超时。
- `min_duration_s`：最短执行时间，没到之前不判成功。
- `stall_s`：本体多长时间不变就判为卡住（原因 `stall`）。
- `timeout_s`：超时（原因 `timeout`）。不写时取提示词库里对应提示词的 p95 时长乘以 `timeout_factor`；提示词库也没有统计时，用默认的 30 秒。
- 没有成功条件的技能（例如脚本原语）在执行器报告做完时算成功。

条件是受限表达式，只能用本体字段、谓词、账本、任务参数等，写法见 [配置参考](configuration.md#表达式)。

## 恢复

失败后按三级处理：

1. 技能的 `on_failure` 表按失败原因（`timeout`、`stall` 或自己在条件里写的 `reason`）决定：重试 N 次（重试前可以先跑 `before_retry` 里的原语，比如 `retract`），或者 `escalate: planner` 交回规划器，或者 `escalate: hold`。
2. 交回规划器时，规划器会看到失败后的画面和记忆，自己决定怎么办。
3. 同一具体调用失败达到 `max_consecutive_failures` 次，进入 HOLD。当前计数按调用分别保存，该调用成功或人工 retry/resume 后清零；中间其他调用成功不会清零，所以并非整个调用流中严格连续的失败次数。

预算（`max_time_s`、`max_skill_calls`、`max_planner_calls`）用完也会 HOLD，错误码是 `E_BUDGET`。

## HOLD 针对哪个调用

每次 HOLD 都针对「手头的主调用」：最近派发（或正由原语做准备）、还没有成功或被人工跳过的那个主调用。操作界面显示的调用、`retry` 和 `skip` 作用的调用都是它：

- HOLD 打断了正在执行的调用（harness 内部错误、执行器拿不出动作、预算、急停等）：这个调用以 `skill_end`（`status: preempted`，`reason: hold`）结束，HOLD 针对它。被打断的是衔接或恢复原语时，HOLD 针对这个原语在为之做准备的主调用。
- 技能失败后 HOLD（恢复表写了 `hold`、连续失败次数到上限），或失败交回规划器后规划出错：HOLD 针对失败的调用。
- 规划器派发了另一个调用之后，之前失败的调用就不再是 HOLD 的对象，不会被 `skip` 误记成完成。
- 技能成功后在规划中 HOLD（例如规划器输出一直不合法）：没有手头的调用，`retry` 和 `skip` 会被拒绝，只能 `resume` 或 `abort`。

`retry` 从头重跑这个调用，所以和规划器的选择一样要检查前置条件：比如 `pick` 已经抓住包裹时被打断，重跑 `pick` 会让策略从它从没见过的状态开始，这时 `retry` 被拒绝，HOLD 保持，可以改用 `skip`（人已经完成了这一步）、`resume`（让规划器重新看一眼）或 `abort`。被拒绝的命令不记入 `human_commands`，日志里有原因。

## 衔接规则

策略最容易在两个技能的衔接处出错：下一个技能开始时的画面，可能是它训练时从没见过的。比如训练数据里放下一个方块之后，接下来总是再把它抓起来；这时让它去抓另一种颜色，提示词往往压不过这个视觉先验。技能文件里的 `transitions` 让 harness 在这类切换时自动插入脚本原语（比如先回到初始姿态，或者带参数地移动到下一个目标上方），把起点拉回训练见过的状态。这些原语对规划器不可见。

找和验证衔接问题的工具：

- `embodied-harness report` 的衔接表：每种「上一步 → 下一步」的成功率，失败按类别分成起点不对（readiness）、目标没找对（grounding）、执行失败（control）；
- `embodied-harness probe`：仿真里从同一个起点把下一个技能重跑若干次，对比干净起点和串联起点，确认是不是起点的问题；
- `embodied-harness suite` 和 `data coverage`：按原子 / 组合、见过 / 没见过分开评测，看新组合要求的衔接在训练数据里有没有。

写法见 [配置参考](configuration.md#衔接规则transitions) 和 [排错](debugging.md#失败归因报表)。

## 记忆和账本

- **记忆**是规划器自己写的一段文字，每次调用时原样还给它，最长 `memory_max_chars` 个字符，超出的部分会被截断。决策被接受后就保存新记忆，此时新技能尚未完成，所以它不能把未来结果记成已经成功。被拒绝的回答（不合法、不成立的 `done`、被挡下的切换）写的记忆不保存，下一次调用看到的还是上一条被接受的记忆。
- **调用历史**（`PlannerContext.history`）是本 episode 已派发的主技能调用，连续重复的只记一次；恢复原语不进入这份列表。它不是成功清单。RoboMME 预测器使用它，JSON 规划器在 `show_history: true` 时也会读取它。
- **账本**（ledger）是 harness 自己记的账：技能成功后按 `effects` 更新，`done_when` 基于它判断任务完成。默认不进规划器的 prompt；`openai_compat` 打开 `show_progress` 时，账本作为「进度」一行给规划器看，`show_state` 再给出谓词和上一步的结果。零样本的规划器最容易数错进度，这两行直接告诉它。
- **经验**（lessons）是从以往运行里总结、人审核过的几句话，写在 prompt 的规则后面。`embodied-harness lessons` 从反复出现的失败里起草，见 [经验文件](configuration.md#经验文件lessons)。

## 动作块和切换

策略一次推理出一段动作（动作块），harness 按控制频率逐个执行。每个动作块带着派发时的指令版本号。技能切换后：

- `handoff: finish_chunk`：先把旧指令剩下的动作执行完，再换新指令的动作。动作比较平滑。新技能的第一个动作块要等旧动作执行完、真正开始执行的那一拍才推理，用的是那一拍的观测，不会拿派发时已经过时的画面去算；它的校验（`min_duration_s`、超时、卡住检测、`hold_s` 计时）以及 `trace.snapshots` 的起点快照也从它自己的第一个动作开始，不会把上一个技能剩下的动作算在新技能头上。
- `handoff: hard`：立刻丢掉旧指令的动作。切换更及时。

websocket 执行器的 `n_action_steps` 决定每个动作块实际执行多少步，剩下的丢掉，下一步重新推理。

## 时钟和线程

- `runtime.clock: sim`：仿真时钟，每个控制周期推进 1/`control_hz` 秒。常用配置同时设置 `planner.threaded: false`，规划同步调用期间仿真停着；时钟类型本身不决定是否启用规划线程。
- `runtime.clock: real`：真实时钟，按 `control_hz` 节拍运行。某一拍超时（比如推理太慢）后，错过的拍直接跳过，对齐到下一个节拍点，不会把几拍的动作连着发出去。上真机时把 `planner.threaded` 设为 `true`，规划器在后台线程运行，控制循环不被阻塞。规划期间机器人保持不动。

## 不用真值

`Observation.info` 只有仿真环境会填，是特权信息。闭环里的规划器、校验器、调度器都不读它（mock oracle 规划器是唯一例外，它本来就是上界对照）。harness 只在 episode 结束时读一次 `info["success"]`（环境自己结束 episode，或 harness 以 `done` 结束且环境报告了这个标志），记为 `env_success`，只用来评分，任何决策都不依赖它。
